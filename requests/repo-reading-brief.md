# 사내 레포를 읽을 수 있는 AI에게 주는 작업 지시

회사 안의 사본에서, 사내 레포를 읽을 수 있는 AI에게 이 파일을 지시문으로 줍니다. 플랫폼 단위와 레포 단위를 쓰게 하기 위한 것입니다.

## 지시

1. 먼저 `AUTHORING.md`와 `company/CONTEXT.md`를 읽고, 원칙, 단위의 형식, 의존성 규칙, 글을 쓰는 규칙을 따릅니다.
2. `units/general/`에 있는 단위 몇 개를 읽어서 글의 분량과 어조를 맞춥니다.
3. 아래 표의 단위를 `units/_template.md` 형식으로 씁니다. 플랫폼 단위는 `company/units/platform-(플랫폼 이름)/`에, 레포 단위는 `company/units/repo-(레포 이름)/`에 저장합니다.
4. 항목마다 근거가 된 파일 경로를 단위 글의 끝에 "근거" 항목으로 적습니다.
5. 레포에서 확인하지 못한 것은 추측하지 않고 "확인 못 함"이라고 적습니다.
6. 개발자가 채운 `company/requests/setup-(레포 이름).md`가 있으면 그 내용을 우선하고, 레포의 내용과 다르면 다른 점을 적습니다.
7. 단위를 쓴 뒤 `company/INDEX.md`의 상태를 "초안"으로 고칩니다.
8. `company/` 밖의 파일은 고치지 않습니다.

## 읽을 레포

읽을 레포의 이름은 `company/CONTEXT.md`에 있습니다. 보통 세 종류입니다.

- 디자인 시스템 패키지의 레포
- 연습 레포
- 제품 레포

## 단위별로 확인할 내용

| 단위 | 적용 대상 | 레포에서 확인할 내용 |
| --- | --- | --- |
| A5 | 플랫폼(웹) | 웹 프로젝트의 package.json에 디자인 시스템 패키지가 적힌 이름과 버전 표기, 버전을 올리는 방식 |
| A9 | 플랫폼(웹) | 회사에서 배포한 스킬과 레포에 있는 AI 도구용 지침 파일의 목록, 각각의 용도 |
| B7 | 플랫폼(웹) | 토큰이 정의된 파일의 위치와 형식, Figma 변수 이름과 코드 토큰 이름의 대응 규칙 |
| B9 | 플랫폼(웹) | 디자인 시스템의 컴포넌트 폴더 구조, 버튼 같은 컴포넌트 하나의 props 목록과 Figma variant의 대응, 기존 디자인 시스템 사용법 스킬이 다루는 범위, 스토리북에서 컴포넌트를 찾는 방법 |
| C6 | 플랫폼(웹) | `skills/README.md`의 작업 규칙이 이 레포들의 구조에서 지켜질 수 있는지, 고쳐야 할 규칙이 있는지 |
| A6 | 레포 | 셋업 절차가 적힌 문서, 필요한 node 버전이 적힌 파일, 사내 패키지 저장소 인증 방법 |
| A7 | 레포 | 개발 서버 실행 명령, 로컬에서 화면을 보려면 로그인이나 테스트 데이터가 필요한지, 스토리북 실행 명령 |
| A8 | 레포 | 화면 코드가 있는 폴더의 구조, 화면 하나를 예로 들어 그 화면의 파일과 사용된 디자인 시스템 컴포넌트 |
| B4, B11 | 레포 | 브랜치 이름 규칙, 커밋 메시지 규칙, PR 템플릿, 자동 검사의 종류, 강제 푸시 차단 여부 |
| C2 | 레포 | 레포의 지침 파일에 "디자이너 작업 범위" 항목이 있으면 그 내용을 그대로 근거로 씁니다. 없으면 화면 코드, 데이터 요청 코드, 비즈니스 로직 코드가 각각 있는 폴더와 서로 분리된 정도를 조사해서 후보를 적고, 개발자의 확인이 필요하다고 표시합니다 |
| D2 | 레포 | API 호출이 정의된 위치, 응답 형태가 정의된 위치 |
| D3, D5 | 레포 | 테스트 파일의 위치와 실행 명령 |

B10(웹 구현과 다른 플랫폼 구현의 비교)은 두 번째 플랫폼의 모듈을 추가할 때 씁니다.
