# 복구 가능한 범위와 실제로 조심할 행동

내 브랜치 안에서 커밋한 내용은 되돌릴 수 있고, main과 다른 사람의 작업에 영향을 주지 않습니다. 실제로 조심해야 하는 행동은 몇 가지뿐이고 아래에 모두 적었습니다. 그 밖의 상황은 대부분 정상적인 과정입니다.

## Figma에서의 판단을 그대로 적용하면 안 되는 이유

Figma는 모두가 파일 하나를 실시간으로 고칩니다. 그래서 누군가 내 시안을 덮어쓰면 작업이 실제로 없어질 수 있습니다.

git은 다릅니다. 각자의 복사본에서 고친 뒤 합치고, 커밋한 내용은 기록에 남습니다. 다른 사람의 변경이 합쳐진 뒤에 내 변경이 최신 코드에서 빠져 있더라도, 내 커밋은 기록에 남아 있어서 다시 적용할 수 있습니다. Figma에서라면 큰 사고인 일이 git에서는 다시 적용하면 되는 일입니다.

## 상황별 등급

| 상황 | 등급 | 실제로 일어난 일과 대응 |
| --- | --- | --- |
| 내 브랜치에서 파일을 잘못 고쳤다 | 정상 | 이전 커밋의 상태로 되돌릴 수 있습니다. main과 다른 사람의 작업에는 영향이 없습니다 |
| 충돌이 났다 | 정상 | 같은 줄을 두 사람이 고쳐서 어느 쪽을 쓸지 고르라는 요청입니다. 양쪽 변경이 모두 남아 있고, 중단하면 충돌 전 상태로 돌아갑니다 |
| PR에 자동 검사 실패가 표시됐다 | 정상 | 문제가 있는 코드가 머지되지 않도록 막는 장치가 동작한 것입니다. 실패 내용을 AI에게 주고 원인을 설명받습니다 |
| 화면이 갑자기 뜨지 않는다 | 정상 | 대개 개발 서버가 꺼졌거나 패키지를 다시 설치해야 하는 경우입니다(단위 A4). 코드가 없어진 것이 아닙니다 |
| 로컬 폴더를 지웠다 | 정상 | 푸시한 내용은 리모트에 있으므로 다시 받으면 됩니다. 푸시하지 않은 커밋과 커밋하지 않은 변경은 없어집니다 |
| 다른 사람의 머지 뒤에 내 변경이 최신 코드에 없다 | 도움 요청 | 내 커밋은 기록에 남아 있습니다. 담당 개발자에게 알리고 다시 적용합니다 |
| 커밋하지 않은 변경을 버리는 명령을 실행했다 | 실제 손실 | 커밋하지 않은 내용은 기록이 없어서 되찾기 어렵습니다 |
| 비밀 키나 고객 데이터가 담긴 파일을 커밋해서 푸시했다 | 즉시 알림 | 발견 즉시 개발자에게 알립니다 |

## 실제로 조심할 행동

1. **커밋하지 않은 채로 오래 작업하지 않습니다.** 복구할 수 있는 것은 커밋한 내용입니다. 의미 있는 변경을 마칠 때마다 커밋합니다.
2. **커밋하지 않은 변경을 버리는 명령을 허락하지 않습니다.** AI가 "변경 사항을 되돌린다", "초기화한다"고 설명하는 명령을 실행하려 하면, 무엇이 없어지는지 먼저 묻습니다.
3. **강제 푸시를 하지 않습니다.** 강제 푸시(force push)는 리모트의 기록을 내 컴퓨터의 기록으로 덮어쓰는 명령입니다. 다른 사람의 커밋이 리모트에서 없어질 수 있습니다.
4. **비밀 값이 든 파일을 커밋하지 않습니다.** 커밋한 내용은 기록에 남는다는 성질이 여기서는 문제가 됩니다. 나중에 파일을 지워도 과거의 커밋에는 남아 있습니다.
5. **실제 서비스의 데이터를 바꾸는 명령을 실행하지 않습니다.** 디자이너의 작업에는 필요하지 않습니다. AI가 그런 명령을 제안하면 멈추고 개발자에게 묻습니다.

main에 직접 푸시하는 것은 보통 레포의 보호 설정으로 막혀 있어서, 실수로 할 수 없습니다.

## 현재 상태를 언제든 물어봐도 됩니다

자신이 어떤 상태에 있는지 모르는 채로 다음 작업을 하지 않습니다. 아래 질문은 아무것도 바꾸지 않으므로 언제든 해도 됩니다.

## AI에게 이렇게 말합니다

- "지금 내가 어느 브랜치에 있고, 커밋하지 않은 변경이 있는지, 리모트와 무엇이 다른지 알려줘."
- "이 명령을 실행하면 없어지는 것이 있는지 먼저 알려줘."
- "충돌이 났어. 어느 파일의 어느 부분에서 누구의 변경과 충돌했는지 설명해줘. 아직 해결하지는 마."
- "내가 이 브랜치에서 만든 커밋 목록을 보여줘."
