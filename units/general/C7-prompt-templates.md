# 지시문 템플릿 모음

다른 단위의 "AI에게 이렇게 말합니다"에 있는 지시문을 상황별로 모았습니다. 괄호 안을 자신의 상황에 맞게 바꿔서 씁니다. 각 지시문이 왜 필요한지는 괄호에 적힌 단위에서 설명합니다.

## 상황을 파악할 때 (아무것도 바꾸지 않습니다)

- "지금 내가 어느 브랜치에 있고, 커밋하지 않은 변경이 있는지, 리모트와 무엇이 다른지 알려줘." (B1, B2)
- "(화면 이름) 화면의 코드 파일이 어디인지, 어떤 디자인 시스템 컴포넌트와 토큰을 쓰고 있는지 부모와 자식 구조로 설명해줘. 코드는 수정하지 마." (B6)
- "이 화면이 서버에서 받아오는 데이터에 어떤 값들이 있는지 목록으로 알려줘. 코드는 수정하지 마." (C3)
- "이 파일에서 뷰에 해당하는 부분과 데이터 요청, 로직에 해당하는 부분을 나눠서 알려줘." (C1)

## 수정을 요청하기 전에

- "(하려는 변경)을 하려면 어떤 파일을 어떻게 바꾸게 되는지 계획만 먼저 말해줘." (A3)
- "이 변경이 뷰만 고치면 되는지, 데이터 요청이나 로직도 바꿔야 하는지 먼저 알려줘." (C1)
- "내 시안에는 (필요한 정보)가 필요해. 이 화면이 이미 받고 있는 데이터에 있는지 확인해줘." (C3)

## 수정 범위를 정할 때

- "이 변경에서 데이터를 가져오는 코드나 로직을 고쳐야 하게 되면, 고치지 말고 멈춰서 무엇이 왜 필요한지 설명해줘." (C1)
- "컴포넌트 정의는 고치지 말고, 이 화면에서 쓰인 자리의 props만 바꿔줘." (B8)
- "기존 컴포넌트의 props로 안 되는 부분이 있으면 스타일을 덮어쓰지 말고 멈춰서 나에게 알려줘." (B8)
- "색과 간격은 숫자로 직접 쓰지 말고 디자인 시스템의 토큰을 써줘. 맞는 토큰이 없으면 알려줘."
- "(요소) 하나에만 여백을 추가하지 말고, 이 묶음의 자식 사이 간격을 바꿔줘." (B6)

## 재사용을 지시할 때

- "이 화면의 (덩어리 이름)은 (다른 화면)의 것과 같은 컴포넌트여야 해. 이미 구현된 것이 있는지 먼저 찾고, 없으면 만들기 전에 어디에 어떤 이름으로 만들지 나에게 확인해줘." (C5)
- "새 컴포넌트를 만들기 전에, 비슷한 기존 컴포넌트가 있는지 검색해서 후보를 보여줘." (C5)

## 데이터가 아직 없을 때

- "없는 값은 API를 고치지 말고, 개발자에게 보낼 요청으로 정리해줘. 어떤 화면에서 어떤 값이 왜 필요한지 적어줘." (C3)
- "필요한 데이터가 아직 없으니 임시 데이터로 뷰를 먼저 만들어줘. 임시 데이터는 파일 하나에 모으고, 임시라는 것을 주석으로 표시해줘." (C1)

## 수정이 끝난 뒤 점검할 때

- "방금 바꾼 내용을 파일별로 무엇을 왜 바꿨는지 설명하고, 뷰가 아닌 파일을 건드렸다면 따로 표시해줘." (B3)
- "내가 요청한 것과 관계없는 변경이 있으면 원래대로 되돌려줘." (B3)
- "이 변경에서 새로 만든 컴포넌트의 목록과 각각이 쓰이는 위치를 알려줘. 비슷한 기존 컴포넌트가 있으면 함께 알려줘." (C5)
- "변경 전과 변경 후의 화면을 비교할 수 있게, 어느 주소에서 무엇을 확인하면 되는지 알려줘."

## 명령을 실행하려 할 때

- "방금 실행하려는 명령이 무엇을 하는 명령인지 한 문장으로 설명해줘." (A3)
- "이 명령을 실행하면 없어지는 것이 있는지 먼저 알려줘." (B2)

## 문제가 생겼을 때

- "화면이 뜨지 않아. 원인을 확인하고 무엇이 문제인지 설명해줘. 아직 고치지는 마." (A4)
- "충돌이 났어. 어느 파일의 어느 부분에서 누구의 변경과 충돌했는지 설명해줘. 아직 해결하지는 마." (B2)
- "자동 검사가 실패했어. 실패한 항목과 원인을 설명해줘. 고치는 방법이 뷰 밖의 파일을 건드린다면 고치지 말고 알려줘."
- "테스트를 통과시키려고 테스트를 고치거나 지우지 마. 테스트가 왜 실패하는지 먼저 설명해줘." (D4)
