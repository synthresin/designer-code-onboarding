# git의 구조: 커밋, 브랜치, 로컬과 리모트, PR

git은 프로젝트 폴더의 변경 기록을 관리하는 도구입니다. 알아야 하는 개념은 네 가지입니다. 커밋은 변경을 기록하는 단위이고, 브랜치는 따로 작업하기 위한 별도의 기록이고, 로컬과 리모트는 복사본이 있는 두 곳이고, PR은 내 변경을 합쳐 달라는 요청입니다. 명령은 AI가 실행하므로 명령어를 외울 필요는 없습니다.

## 커밋: 변경을 기록하는 단위

파일을 고치고 저장하는 것만으로는 git에 기록되지 않습니다. "여기까지의 변경을 기록한다"고 명시적으로 남기는 것이 커밋입니다. 커밋에는 무엇을 바꿨는지 설명하는 메시지가 붙습니다.

커밋은 쌓입니다. 프로젝트의 역사는 커밋이 순서대로 이어진 기록이고, 어느 커밋의 상태로든 돌아가 볼 수 있습니다. 한번 만든 커밋은 쉽게 없어지지 않습니다. 이 성질 덕분에 대부분의 실수를 복구할 수 있습니다(단위 B2).

## 브랜치: 따로 작업하기 위한 별도의 기록

제품에 실제로 쓰이는 코드의 기록을 보통 main이라고 부릅니다. 브랜치는 main의 어느 시점에서 시작해서 따로 커밋을 쌓아 가는, 이름이 붙은 별도의 기록입니다.

작업을 시작할 때 브랜치를 새로 만들고 그 안에서 고칩니다. 내 브랜치에서 무엇을 하든 main과 다른 사람의 브랜치에는 영향이 없습니다. 작업 하나에 브랜치 하나를 씁니다.

## 로컬과 리모트: 복사본이 있는 두 곳

- 로컬은 내 컴퓨터에 있는 레포의 복사본입니다.
- 리모트는 GitHub에 있는 레포입니다. 팀 전체가 기준으로 삼는 곳입니다.

두 곳은 자동으로 같아지지 않습니다. 내 컴퓨터에서 커밋해도 GitHub에는 올라가지 않고, 다른 사람이 GitHub에 올린 변경도 내 컴퓨터에 자동으로 들어오지 않습니다. 옮기는 작업을 따로 합니다.

- 푸시(push): 내 컴퓨터의 커밋을 GitHub로 보냅니다.
- 풀(pull): GitHub에 새로 올라온 커밋을 내 컴퓨터로 받아옵니다.

## PR: 내 변경을 합쳐 달라는 요청

PR(pull request)은 내 브랜치의 변경을 main에 합쳐 달라고 GitHub에서 올리는 요청입니다. PR을 올리면 세 가지 일이 일어납니다.

1. 다른 사람이 변경 내용을 보고 의견을 남기거나 승인합니다. 이것을 리뷰라고 합니다.
2. 자동 검사가 돌아서 코드에 문제가 없는지 확인합니다.
3. 승인과 검사를 통과하면 변경이 main에 합쳐집니다. 이것을 머지(merge)라고 합니다.

main에 직접 올리지 않고 PR을 거치기 때문에, 내 변경은 다른 사람이 확인한 뒤에야 제품 코드에 들어갑니다.

## 작업 한 번의 흐름

1. main의 최신 내용을 내 컴퓨터로 받아옵니다.
2. 새 브랜치를 만듭니다.
3. 파일을 고치고 커밋합니다. 여러 번 해도 됩니다.
4. 브랜치를 GitHub로 푸시합니다.
5. PR을 올리고 리뷰를 받습니다.
6. 머지됩니다.

레포마다 브랜치 이름 규칙 같은 세부 절차가 다릅니다. 그 내용은 레포 단위 B4에 있습니다.

## Figma와 비교하면

| Figma | git |
| --- | --- |
| 버전 기록에 이름을 붙여 저장합니다 | 커밋 |
| 브랜치 기능으로 따로 작업한 뒤 병합을 요청합니다 | 브랜치와 PR |
| 파일은 클라우드에 하나만 있습니다 | 로컬과 리모트에 복사본이 따로 있습니다 |

대응이 맞지 않는 지점은 세 번째 줄입니다. Figma는 고치는 즉시 모두에게 보이지만, git에서는 커밋하고 푸시해야 다른 사람이 볼 수 있습니다. 반대로, 푸시하기 전까지는 무엇을 해도 다른 사람에게 영향이 없습니다.

## AI에게 이렇게 말합니다

- "지금 내가 어느 브랜치에 있고, 커밋하지 않은 변경이 있는지, 리모트와 무엇이 다른지 알려줘."
- "main의 최신 내용을 받아오고 이 작업을 위한 새 브랜치를 만들어줘. 실행하기 전에 각 명령이 무엇을 하는지 설명해줘."
- "지금까지의 변경을 커밋해줘. 커밋 메시지는 이 레포의 규칙에 맞춰줘."
