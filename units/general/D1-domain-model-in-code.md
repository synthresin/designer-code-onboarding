# 도메인 모델이 코드에 있는 위치: n:m 관계가 코드와 데이터베이스에서 표현되는 방식

도메인 모델은 서비스가 다루는 개체와 그 개체들 사이의 관계입니다. 스펙을 짤 때 "구성원 한 명은 팀 하나에만 속하는가, 여러 팀에 속할 수 있는가"를 따지는 것이 도메인 모델을 정하는 일입니다. 이 관계는 디자인 문서에만 있지 않고, 데이터베이스와 API 응답과 화면에 같은 모양으로 나타납니다. 그래서 관계 하나를 바꾸면 세 곳이 모두 바뀝니다.

## 관계의 종류

| 관계 | 뜻 | 예 |
| --- | --- | --- |
| 1:1 | 한쪽 하나에 다른 쪽 하나 | 구성원 한 명에 인사 기록 카드 하나 |
| 1:n | 한쪽 하나에 다른 쪽 여럿 | 구성원 한 명에 휴가 신청 여러 건. 신청 한 건은 한 사람의 것입니다 |
| n:m | 양쪽 모두 여럿 | 구성원 한 명이 프로젝트 여러 개에 참여하고, 프로젝트 하나에 구성원 여러 명이 참여합니다 |

## 같은 관계가 세 곳에 나타납니다

구성원과 프로젝트의 n:m 관계를 예로 듭니다.

**데이터베이스에서.** 데이터는 표의 형태로 저장됩니다. 구성원 표와 프로젝트 표가 따로 있고, n:m 관계는 "어느 구성원이 어느 프로젝트에 참여하는가"만 적는 세 번째 표로 저장됩니다. 참여 한 건이 한 줄입니다. 참여에 딸린 정보(역할, 참여 시작일)가 있다면 이 세 번째 표에 들어갑니다.

**API 응답에서.** 구성원을 조회한 응답 안에 프로젝트의 목록이 들어 있거나, 프로젝트를 조회한 응답 안에 구성원의 목록이 들어 있습니다. 어느 방향으로 조회할 수 있는지는 API가 어떻게 만들어져 있는지에 달려 있습니다.

```
{
  "name": "김하늘",
  "projects": [
    { "name": "모바일 개편", "role": "디자인" },
    { "name": "결제 개선", "role": "리서치" }
  ]
}
```

**화면에서.** 구성원 상세 화면에 프로젝트 목록이 있고, 프로젝트 상세 화면에 구성원 목록이 있습니다. 프로젝트를 고르는 입력은 여러 개를 고를 수 있는 형태가 됩니다.

## 관계가 화면의 형태를 정합니다

| 관계 | 고르는 입력 | 보여 주는 형태 |
| --- | --- | --- |
| 구성원은 팀 하나에 속한다 | 하나만 고르는 입력 | 값 하나 |
| 구성원은 여러 팀에 속할 수 있다 | 여러 개를 고르는 입력 | 목록. 주 소속을 따로 표시할지도 정해야 합니다 |

하나만 고르는 입력을 여러 개 고르는 입력으로 바꾸는 것은 화면에서는 컴포넌트 하나를 바꾸는 일로 보입니다. 하지만 실제로는 1:n을 n:m으로 바꾸는 일이어서, 데이터베이스의 구조와 API의 응답 형태와 이 관계를 쓰는 모든 화면이 함께 바뀌어야 합니다. 이미 저장된 데이터를 새 구조로 옮기는 작업도 필요합니다.

이것을 알면 스펙을 논의할 때 변경의 크기를 미리 가늠할 수 있습니다. 관계는 그대로 두고 보여 주는 방식만 바꾸는 변경은 작고, 관계 자체를 바꾸는 변경은 큽니다.

## 코드에서 도메인 모델을 볼 수 있는 곳

- 화면 쪽 코드에는 API 응답의 형태를 적어 둔 정의가 있는 경우가 많습니다. 어떤 개체에 어떤 값이 있고, 어떤 값이 목록인지가 적혀 있습니다.
- 서버 쪽 코드에는 데이터베이스의 표와 대응하는 모델 정의가 있습니다.

디자이너가 직접 고칠 대상은 아니지만, AI에게 읽게 해서 현재의 관계가 어떻게 되어 있는지 확인할 수 있습니다. 스펙을 쓰기 전에 현재 상태를 확인하는 용도로 유용합니다.

## AI에게 이렇게 말합니다

- "이 코드에서 구성원과 팀의 관계가 1:n인지 n:m인지 확인해줘. 근거가 되는 정의의 위치도 알려줘. 코드는 수정하지 마."
- "이 화면이 받는 응답의 형태를, 개체와 그 사이의 관계로 정리해서 설명해줘."
- "이 관계를 n:m으로 바꾸려면 어떤 화면과 어떤 API가 영향을 받는지 목록으로 알려줘. 바꾸지는 마."
