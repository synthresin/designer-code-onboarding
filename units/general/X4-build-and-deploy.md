# 빌드와 배포: 머지된 코드가 사용자에게 도달하는 과정

PR이 머지됐다고 해서 그 변경이 곧바로 사용자에게 보이는 것은 아닙니다. 머지는 코드가 main에 들어갔다는 뜻이고, 그 코드가 사용자가 쓰는 서비스에 반영되려면 빌드와 배포를 거쳐야 합니다. 이 과정은 대부분 자동화되어 있고 디자이너가 직접 다룰 일은 없지만, "머지됐는데 왜 아직 안 보이나요"라는 질문의 답이 여기에 있습니다.

## 빌드: 코드를 실행할 수 있는 형태로 바꿉니다

레포에 있는 코드는 사람이 읽고 고치기 좋게 쓴 것이고, 파일 수천 개로 나뉘어 있습니다. 빌드는 이 코드를 브라우저가 빠르게 받아서 실행할 수 있는 파일 몇 개로 변환하고 묶는 작업입니다. 이 과정에서 코드에 문제가 있으면 빌드가 실패합니다.

내 컴퓨터의 개발 서버는 고칠 때마다 곧바로 반영되도록 만들어진 것이라서 빌드 결과와 완전히 같지는 않습니다. 드물게 개발 서버에서는 되는데 빌드에서 실패하는 경우가 있고, PR의 자동 검사에 빌드가 포함되어 있는 이유입니다.

## 배포: 빌드 결과를 사용자가 접속하는 곳에 올립니다

배포는 빌드된 파일을 서버에 올려서, 사용자가 접속하는 주소에서 새 버전이 제공되게 하는 작업입니다.

## 환경이 여러 개 있습니다

같은 서비스가 용도에 따라 여러 곳에서 따로 실행됩니다. 이름은 회사마다 다르지만 보통 세 가지입니다.

| 환경 | 용도 | 데이터 |
| --- | --- | --- |
| 로컬 | 내 컴퓨터. 개발하면서 확인합니다 | 테스트용 데이터 |
| 스테이징 | 회사 안에서 확인하는 용도입니다. 운영 환경과 비슷하게 만들어 둡니다 | 테스트용 데이터 |
| 운영 | 실제 사용자가 쓰는 서비스입니다 | 실제 고객의 데이터 |

머지된 코드는 보통 스테이징에 먼저 배포되고, 확인을 거친 뒤 운영에 배포됩니다. 그래서 변경이 "스테이징에는 나갔고 운영에는 아직"인 기간이 있습니다.

## 머지에서 사용자까지

1. PR이 main에 머지됩니다.
2. 자동화된 도구가 main의 코드를 빌드합니다.
3. 빌드 결과가 스테이징에 배포됩니다.
4. 정해진 시점에 운영에 배포됩니다. 머지될 때마다 자동으로 나가는 회사도 있고, 정해진 요일에 모아서 내보내는 회사도 있습니다.

머지와 운영 배포 사이의 간격은 회사와 제품마다 다릅니다. 몇 분일 수도 있고 며칠일 수도 있습니다.

## 알아 두면 쓸모 있는 것

- **되돌리기.** 배포한 뒤 문제가 발견되면 이전 버전으로 되돌릴 수 있습니다. 코드의 변경을 되돌리는 커밋을 만들어 다시 배포하는 방식이 일반적입니다.
- **기능 플래그.** 코드는 배포해 두고, 그 기능을 켜고 끄는 것을 설정으로 따로 조절하는 방식입니다. 배포는 됐지만 일부 사용자에게만 보이거나 아직 아무에게도 보이지 않는 상태가 가능합니다. 머지도 배포도 됐는데 화면에 안 보인다면 이 경우일 수 있습니다.
- **앱은 다릅니다.** 웹은 배포하면 사용자가 다음에 접속할 때 새 버전을 받습니다. 설치해서 쓰는 앱은 스토어의 심사와 사용자의 업데이트를 거쳐야 해서 반영이 더 느립니다.

- "내 PR의 변경이 어느 환경까지 배포됐는지 확인할 방법이 있는지 알려줘."
