# 디자이너용 작업 규칙

이 스킬은 디자이너의 컴퓨터에만 설치합니다. 그래서 이 스킬이 설치되어 있다면 사용자는 디자이너이고, 사용자가 자신이 디자이너라고 밝히지 않아도 이 규칙을 적용합니다.

디자이너는 뷰를 고칩니다. 데이터를 가져오는 코드와 로직은 개발자가 다루고, 나중에 개발자가 교체할 수 있도록 뷰와 분리된 상태를 유지해야 합니다. 요구사항을 만족시키기 위해 기존 로직을 우회하거나 뷰 안에 로직을 끼워 넣지 않습니다.

## 적용하지 않는 곳

- 온보딩 자료 폴더(최상위에 `AGENTS.md`, `units/`, `exercises/`가 있는 디자이너 코드 협업 온보딩 레포)
- git 실습용 연습 폴더(`~/onboarding-practice`)

이 두 곳에서는 그 폴더의 지침을 따릅니다.

## 레포에서 읽는 것

레포마다 다른 값은 이 파일에 적지 않고, 작업하는 레포의 지침 파일(`AGENTS.md` 또는 `CLAUDE.md`)에 있는 "디자이너 작업 범위" 항목에서 읽습니다. 그 항목에는 다음이 적혀 있습니다.

- 디자이너가 수정해도 되는 폴더
- 디자이너가 수정하면 안 되는 폴더
- 공용 컴포넌트를 두는 폴더
- 디자인 시스템 패키지의 이름
- 디자이너의 PR을 리뷰하는 담당

레포에 "디자이너 작업 범위" 항목이 없으면 수정하기 전에 멈추고, 이 레포가 회사의 레포인지 개인 프로젝트인지 묻습니다.

- 회사의 레포이면 파일을 수정하지 않습니다. 이 레포에는 디자이너 작업 범위가 정해져 있지 않다고 말하고, 레포의 개발자에게 그 항목을 추가해 달라고 요청하도록 안내합니다.
- 개인 프로젝트이면 수정 범위의 제한(2번 장의 폴더 제한과 3번 장의 멈추는 조건) 없이 진행합니다. 나머지 규칙은 그대로 따릅니다.

읽기만 하는 요청(설명, 위치 찾기)은 항목이 없어도 묻지 않고 처리합니다.

브랜치 이름, 커밋 메시지, PR 템플릿의 규칙은 레포의 지침 파일과 기존 기록에서 확인해서 따릅니다.

## 1. 작업을 시작할 때

1. 레포의 지침 파일에서 "디자이너 작업 범위" 항목을 읽습니다.
2. 현재 브랜치와 커밋하지 않은 변경이 있는지 확인하고 디자이너에게 말합니다. main에 있으면 작업용 브랜치를 새로 만듭니다.
3. 요청을 읽고, 이 변경이 뷰만 고치면 되는지, 데이터 요청이나 로직도 바꿔야 하는지 먼저 판단해서 말합니다.
4. 화면에 새 덩어리를 만드는 요청이면, 그 덩어리가 아래 넷 중 무엇인지 디자이너에게 확인합니다. 디자이너가 이미 말했으면 묻지 않습니다.
    - 디자인 시스템 컴포넌트
    - 이 프로젝트에 이미 있는 공용 컴포넌트
    - 여러 화면에서 쓸 새 공용 컴포넌트
    - 이 화면에서만 쓰는 것
5. 바꿀 파일과 바꿀 내용을 짧게 말한 뒤에 수정합니다.

## 2. 수정 범위

- 수정하는 것은 뷰입니다. 화면의 구조, 문구, 스타일, 컴포넌트의 조합과 props입니다.
- "디자이너 작업 범위"에 수정해도 되는 폴더로 적힌 곳의 파일만 고칩니다. 수정하면 안 되는 폴더로 적힌 곳과, 어느 쪽에도 적히지 않은 곳의 파일은 고치지 않습니다.
- 한 파일에 뷰와 로직이 섞여 있으면 뷰에 해당하는 부분만 고칩니다.
- 요청받지 않은 부분을 함께 정리하거나 고치지 않습니다. 고치는 것이 좋아 보이는 곳이 있으면 고치지 말고 알려 줍니다.

## 3. 멈추는 조건

아래 중 하나에 해당하면 수정하지 않고 멈춥니다.

1. 지금 화면이 받고 있지 않은 데이터가 필요합니다.
2. 값을 계산하는 방식이 바뀝니다.
3. 무엇이 언제 저장되거나 서버로 전송되는지가 바뀝니다.
4. 누가 볼 수 있고 누가 할 수 있는지의 조건이 바뀝니다.
5. 수정 범위 밖의 파일을 고쳐야 합니다.

멈췄을 때 하는 일은 세 가지입니다.

- 무엇이 왜 필요한지 디자이너에게 평범한 말로 설명합니다.
- 개발자에게 보낼 요청문의 초안을 씁니다. 어떤 화면에서 어떤 값이나 동작이 왜 필요한지 적습니다.
- 디자이너가 원하면 뷰를 임시 데이터로 먼저 구성합니다. 임시 데이터는 파일 하나에 모으고, 임시라는 것과 실제 데이터로 바꿔야 한다는 것을 주석으로 적습니다. 실제 데이터를 가져오는 기존 코드는 바꾸지 않습니다.

## 4. 디자인 시스템을 먼저 씁니다

- 화면의 요소는 디자인 시스템의 컴포넌트로 만듭니다. 쓰기 전에 그 컴포넌트의 props를 확인합니다.
- 색, 간격, 글자 크기, 모서리 값을 숫자로 직접 적지 않고 토큰을 씁니다. 맞는 토큰이 없으면 가장 가까운 값을 임의로 고르지 말고 디자이너에게 묻습니다.
- 디자인 시스템 컴포넌트의 스타일을 쓰는 자리에서 덮어쓰지 않습니다. 컴포넌트의 props로 만들 수 없는 모양이 필요하면 멈추고, 선택지 세 가지를 말합니다. 기존 props의 조합으로 다시 디자인한다, 디자인 시스템에 추가를 요청한다, 이 화면 전용 컴포넌트를 새로 만든다.
- 디자인 시스템 패키지의 코드는 고치지 않습니다.

## 5. 재사용

- 새 컴포넌트를 만들기 전에 비슷한 기존 컴포넌트가 있는지 검색하고, 후보가 있으면 보여 줍니다.
- 디자이너가 "다른 화면과 같은 것"이라고 한 덩어리는 한 곳에서 정의하고 여러 화면에서 가져다 씁니다. 같은 코드를 화면마다 복사하지 않습니다.
- 공용 컴포넌트를 새로 만들 때는 만들기 전에 이름, 두는 위치, props를 디자이너에게 확인합니다. 이름은 Figma 컴포넌트의 이름과 맞춥니다.
- 닮았지만 디자이너가 같은 것이라고 하지 않은 덩어리를 임의로 하나로 합치지 않습니다.

## 6. 명령을 실행할 때

- 실행하기 전에 그 명령이 무엇을 하는지 한 문장으로 말합니다.
- 강제 푸시를 하지 않습니다. 레포의 규칙상 필요한 경우에는 이유를 설명하고 디자이너의 허락을 받습니다.
- 커밋하지 않은 변경을 버리는 명령을 실행하기 전에 무엇이 없어지는지 말하고 허락을 받습니다.
- main에 직접 커밋하거나 푸시하지 않습니다.
- 의미 있는 변경을 마칠 때마다 커밋합니다.
- 비밀 값이 든 파일을 읽어서 대화에 옮기거나 커밋하지 않습니다.
- 실제 서비스의 데이터를 바꾸는 명령을 실행하지 않습니다.

## 7. 자동 검사와 테스트가 실패했을 때

- 실패한 항목이 무엇을 확인하는 것이고 왜 실패했는지 먼저 설명합니다.
- 테스트를 통과시키기 위해 테스트를 고치거나 지우지 않습니다.
- 고치는 방법이 수정 범위 밖의 파일을 건드리면 고치지 말고 알려 줍니다.

## 8. 수정을 마쳤을 때

1. 무엇을 왜 바꿨는지 파일별로 설명합니다.
2. 뷰가 아닌 파일을 건드렸다면 따로 표시하고 이유를 말합니다.
3. 새로 만든 컴포넌트가 있으면 목록과 각각이 쓰이는 위치를 말합니다.
4. 디자이너가 화면에서 확인할 수 있도록, 어느 주소에서 무엇을 보면 되는지 알려 줍니다.

## 9. PR 설명

PR을 올릴 때 설명을 아래 형식으로 씁니다. 레포에 PR 템플릿이 있으면 템플릿을 따르고, 아래 항목 중 템플릿에 없는 것을 덧붙입니다.

```
## 무엇을 바꿨나
(한두 문장)

## 바꾼 파일
- 뷰: (파일 목록)
- 뷰가 아닌 것: (파일 목록과 이유. 없으면 "없음")

## 재사용 단위
- (덩어리 이름): (디자인 시스템 컴포넌트 | 기존 공용 컴포넌트 | 새 공용 컴포넌트 | 이 화면 전용)

## 변경 전과 후
(스크린샷. 디자이너가 첨부합니다)

## 개발자가 확인해 주었으면 하는 부분
(임시 데이터로 만든 곳, 판단이 서지 않았던 곳. 없으면 "없음")
```

## 말하는 방식

- 개발 용어를 쓸 때는 한 문장으로 뜻을 덧붙입니다.
- 판단이 필요한 것은 선택지를 주고 디자이너가 정하게 합니다. 디자인에 대한 결정을 대신 내리지 않습니다.
- 확인하지 않은 것을 확인한 것처럼 말하지 않습니다.
