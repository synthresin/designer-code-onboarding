# 스킬 설계

스킬 두 개를 만들어 회사에서 쓰는 AI 코딩 앱에 배포합니다. 이 파일은 설계이고, 스킬 파일은 플랫폼 단위와 레포 단위가 채워진 뒤에 만듭니다.

## 1. 온보딩 진행 스킬

단위 글을 읽고 디자이너의 AI 코딩 앱 안에서 과정을 진행시킵니다.

1. 진행 기록 파일을 읽어 이 사람이 어느 단위까지 마쳤는지 확인합니다.
2. 다음 단위의 글을 읽고 그 내용을 설명합니다. 설명을 스스로 지어내지 않고 글에 적힌 내용을 전달합니다.
3. 실습 단위이면 필요한 명령을 AI가 실행합니다. 디자이너는 명령을 직접 입력하지 않고, AI는 실행하기 전에 그 명령이 무엇을 하는지 한 문장으로 말합니다.
4. 완료 여부를 대화가 아니라 실제 상태로 확인합니다. 예를 들어 브랜치가 만들어졌는지, PR이 열렸는지를 명령으로 조회합니다.
5. 진행 기록을 갱신하고, 막혔던 지점과 나온 질문을 기록합니다. 이 기록을 모아서 단위 글을 고칩니다.

셋업 단위(A6)에서는 개발자가 채운 `company/requests/setup-(레포 이름).md`의 명령으로 설치와 점검을 실행하고, 실패한 항목이 있으면 어떤 항목이 왜 실패했는지 설명합니다.

## 2. 디자이너용 작업 규칙 스킬

온보딩이 끝난 뒤에도 디자이너의 모든 코드 작업에 적용합니다.

1. 수정 범위는 뷰 파일입니다. 어느 폴더가 뷰인지는 레포 단위 C2의 폴더 목록을 따릅니다. 범위 밖의 파일을 고쳐야 하게 되면 고치지 않고 멈춰서, 무엇이 왜 필요한지 설명합니다.
2. 요구사항이 현재 화면에 들어오는 데이터로 구현되지 않으면, 기존 로직을 우회해서 구현하지 않습니다. 필요한 데이터를 목록으로 정리해 개발자에게 보낼 요청문을 작성하고, 뷰는 임시 데이터로 먼저 구성합니다. 임시 데이터는 한 파일에 모아서, 개발자가 나중에 그 파일만 실제 데이터 연결로 교체하면 되게 합니다.
3. 디자인 시스템의 컴포넌트와 토큰을 먼저 사용합니다. 색과 간격을 숫자로 직접 적지 않습니다. 디자인 시스템에 없는 것이 필요하면 만들기 전에 디자이너에게 확인합니다.
4. 새 컴포넌트를 만들기 전에 비슷한 기존 구현을 검색하고, 디자이너에게 이 덩어리가 다른 화면에서도 쓰이는지 묻습니다.
5. 명령을 실행하기 전에 그 명령이 무엇을 하는지 한 문장으로 말합니다. 강제 푸시와 커밋하지 않은 변경을 버리는 명령은 실행하지 않습니다.
6. PR 설명을 정해진 형식으로 작성합니다. 바꾼 파일을 뷰와 뷰가 아닌 것으로 나눠 적고, 재사용 단위, 전후 스크린샷, 개발자가 확인해야 할 부분을 적습니다.
