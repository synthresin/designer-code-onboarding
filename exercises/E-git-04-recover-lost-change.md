# 사라진 것처럼 보이는 변경을 되찾기

## 목표

"내가 올린 변경이 다른 사람의 머지 뒤에 없어졌다"는 상황을 일부러 만들고, 내 커밋을 찾아서 다시 적용합니다. 마지막에는 실제로 되찾을 수 없는 경우를 안전하게 겪어 봅니다.

## 시작할 때의 상태

`me` 폴더가 `main`에 있고 리모트의 최신과 같으며 커밋하지 않은 변경이 없습니다.

## 진행

1. **내 변경을 main에 합치기.** AI가 `git switch -c practice/lost-change`로 브랜치를 만듭니다. 디자이너가 `copy.md`의 화면 제목을 무엇으로 바꿀지 정하고, AI가 고쳐서 커밋합니다. AI가 이 커밋의 번호를 디자이너에게 알려 줍니다. 그다음 브랜치를 푸시하고, `git switch main`, `git merge practice/lost-change`, `git push origin main`으로 `main`에 합칩니다. AI가 말합니다. "실제 작업에서는 PR이 머지된 상태입니다."
2. **동료가 덮어쓰기.** AI가 말합니다. "이제 동료가 문구를 정리하다가 화면 제목을 예전 문구로 되돌려 버린 상황을 만들겠습니다." AI가 `teammate` 폴더에서 `git pull origin main`을 한 뒤, 화면 제목을 원래의 "휴가 신청"으로 되돌리고 버튼 문구도 하나 고쳐서 "문구 정리"라는 커밋으로 `main`에 올립니다.
3. **최신 내용 받기.** AI가 `me` 폴더에서 `git pull origin main`을 실행하고 `copy.md`의 화면 제목을 보여 줍니다. 디자이너가 고친 문구가 없습니다.
4. **멈추고 묻기.** AI가 묻습니다. "변경이 없어진 것처럼 보입니다. 정말 없어졌을까요? 어떻게 확인할 수 있을까요?"
5. **내 커밋 찾기.** AI가 `git log --oneline -- copy.md`를 실행합니다. 디자이너의 커밋이 기록에 그대로 있고, 그 뒤에 동료의 "문구 정리" 커밋이 있습니다. AI가 `git show (동료의 커밋 번호)`로 동료의 커밋이 화면 제목 줄을 바꾼 것을 보여 줍니다.
6. **다시 적용하기.** AI가 `git switch -c practice/reapply`로 새 브랜치를 만들고 `git cherry-pick (디자이너의 커밋 번호)`를 실행합니다. 실행하기 전에 "그 커밋에 들어 있던 변경을 지금 브랜치에 다시 적용합니다"라고 말합니다. `copy.md`의 화면 제목이 디자이너의 문구로 돌아옵니다.
7. **실제로 되찾을 수 없는 경우 겪어 보기.** AI가 `notes.md` 끝에 "- 임시 메모" 한 줄을 추가하고 커밋하지 않습니다. AI가 말합니다. "이 줄은 커밋하지 않았습니다. 이제 커밋하지 않은 변경을 버리는 명령을 실행하겠습니다. 실행하면 이 줄은 되찾을 수 없습니다. 진행할까요?" 디자이너가 허락하면 `git restore notes.md`를 실행하고, 그 줄이 없어진 것과 기록 어디에도 남아 있지 않은 것(`git log --oneline -- notes.md`)을 보여 줍니다.

## 완료 확인

- `practice/reapply` 브랜치의 `copy.md`에서 화면 제목이 디자이너의 문구입니다.
- `git log --oneline -- copy.md`에 디자이너의 원래 커밋과 다시 적용한 커밋이 모두 있습니다.
- `git status`에 커밋하지 않은 변경이 없습니다.

## 마친 뒤에 말해 줄 것

- 3번에서 본 상황이 "PR을 올려서 머지됐는데 다른 사람의 머지 뒤에 없어졌다"는 상황입니다. 내 커밋은 기록에 남아 있었고, 다시 적용하는 데 명령 하나가 들었습니다.
- 실제 작업에서 이 상황을 만나면 직접 다시 적용하기 전에 담당 개발자에게 알립니다. 동료가 일부러 되돌린 것일 수도 있기 때문입니다.
- 7번에서 없어진 줄은 커밋하지 않았기 때문에 되찾을 수 없었습니다. 복구할 수 있는 것은 커밋한 내용입니다. 그래서 의미 있는 변경을 마칠 때마다 커밋합니다.
